# Сайт LGS: тест «Архетип личности»

Лендинг, тест из 17 вопросов, страница результата, сегментация, сбор лидов и админка для Института современного NLP / LGS (ТОО «LOGOS»). Сделано по ТЗ версии 1 от 18 ноября 2026.

Что ждёт заказчика, собрано в [CONTENT_TODO.md](CONTENT_TODO.md).

## Запуск

```bash
npm install
```

```bash
npm run dev
```

Сайт откроется на http://localhost:3000. Без `DATABASE_URL` используется встроенный Postgres (PGlite), данные лежат в `.data/pglite`. Для админки задайте `ADMIN_PASSWORD` в `.env.local` (образец в `.env.example`).

| Команда | Что делает |
|---|---|
| `npm test` | Модульные тесты: подсчёт архетипа, сегментация, контент, расписание сообщений, телефон |
| `npm run test:e2e` | Сквозной путь «лендинг → тест → контакт → результат» в Playwright. Перед первым запуском: `npx playwright install chromium` |
| `npm run typecheck` | Проверка типов |
| `npm run build` | Сборка |

Тест контента проверяет, что в каждом вопросе блока B четыре архетипа и каждый встречается 8 раз. После правки вопросов запустите `npm test`.

Тексты со статусом `draft` показываются на сайте. При локальной разработке рядом с ними стоит пометка «Черновик», в админке виден счётчик неутверждённых.

## Как это работает

1. Тест хранит ответы в `localStorage` и продолжается с места остановки.
2. После 17-го ответа сервер считает архетип и сегмент и создаёт запись в `leads` со статусом `test_done`. Человек видит короткий результат на `/result/[publicId]`: архетип, диаграмму, сильную сторону.
3. Форма контакта дописывает имя, WhatsApp и дату согласия. Статус меняется на `contact_given`, лид уходит в GetCourse, в CRM-вебхук и получает первое сообщение со ссылкой на результат. Та же страница показывает полный разбор.
4. Кнопки следующего шага зависят от сегмента. Оплата идёт на стороне GetCourse, вебхук меняет статус на `consult_paid`, `intensive_paid` или `intensive_vip_paid`.

Правила подсчёта: баллы по шести кодам; при равенстве побеждает архетип, который чаще выбран в вопросах B1, B3, B7, B10; если и там равенство, порядок S, D, N, V, O, B. Разница первого и второго в 1 балл или меньше подаётся как связка. Тест перебирает все 16 777 216 комбинаций ответов блока B.

## Деплой на Vercel

1. Создайте базу Postgres (Supabase или Vercel Postgres) и задайте `DATABASE_URL`. Таблицы создаются при первом обращении.
2. Задайте переменные из `.env.example`. Обязательные: `DATABASE_URL`, `SITE_URL`, `ADMIN_PASSWORD`. Для оплаты: `GETCOURSE_*`. Для цепочки сообщений: `CRON_SECRET`.
3. `vercel.json` запускает крон цепочки каждые 10 минут. На тарифе Hobby Vercel разрешает крон только раз в сутки: нужен тариф Pro или внешний планировщик, который вызывает `/api/cron/funnel` с заголовком `Authorization: Bearer <CRON_SECRET>`.

## Интеграции

- **GetCourse.** Без `GETCOURSE_ACCOUNT` и `GETCOURSE_API_KEY` работает заглушка с логом. Ссылки на оплату берутся из `GETCOURSE_OFFER_*`; пока их нет, кнопка ведёт на страницу «оплата подключается».
- **WhatsApp.** Интерфейс `sendMessage(to, templateId, vars)` в `integrations/whatsapp.ts`. Провайдер не выбран, по умолчанию заглушка. Новый провайдер добавляется в `PROVIDERS`.
- **CRM.** `LEAD_WEBHOOK_URL` получает полный объект лида при каждом изменении статуса.
- **Счётчики.** Meta Pixel, GA4 и Яндекс Метрика загружаются только после согласия в баннере cookie. События воронки дублируются в таблицу `events`, по ней строится воронка в админке.

## Ограничения первой версии

- Ограничение частоты по IP хранится в памяти процесса. На Vercel у каждого экземпляра память своя, так что это защита от простых ботов, а не точный лимит.
- Событие `Purchase` уходит в счётчики со страницы `/thanks`, когда оплату уже подтвердил вебхук. Если человек не вернулся на сайт после оплаты, покупка видна только в базе и в CRM. Для точной передачи в Meta нужен Conversions API.
- События в отладчиках Pixel, GA4 и Метрики не проверялись: идентификаторы счётчиков ещё не заданы.
- LCP и вес первого экрана на мобильном 4G не измерялись.
- PDF результата не генерируется: есть постоянная ссылка `/result/[publicId]`.
